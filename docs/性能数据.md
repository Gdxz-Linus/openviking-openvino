# 性能数据

全部为本机实测（Intel Arc 核显，OpenVINO 2024）。测量条件在每组数据前注明。

## 一、纯 GPU 收益

条件：同一模型 `harrier-ov-int8`、同一文本、同一后端，唯一变量是
`OPENVIKING_OV_DEVICE`。

| 档位 | 字符数 | CPU | GPU | 提速 |
| --- | --- | --- | --- | --- |
| 短 | 30 字 | 55.5 ms | 34.5 ms | 1.6 倍 |
| 中 | 1800 字 | 4255.8 ms | 672.6 ms | 6.3 倍 |
| 长 | 6600 字（触顶 4096 token） | 30149.6 ms | 3985.5 ms | 7.6 倍 |

## 二、两种形态的端到端对比

| 指标 | 进程内 OpenVINO | HTTP 独立服务 |
| --- | --- | --- |
| 检索中位延迟 | 43 ms | 273 到 386 ms |
| 嵌入调用开销 | 直接函数调用 | FastAPI + Pydantic + HTTP |
| 差距来源 | — | 请求处理与序列化，约 6 到 9 倍 |

HTTP 形态的额外开销分析（2026-11-09 实测）：

| 环境 | 单次耗时 |
| --- | --- |
| 进程内直接调用 `embed_one` | 中位 21.3 ms |
| requests.Session | 中位 105.8 ms |
| httpx.AsyncClient | 中位 97.9 ms |
| openai.AsyncOpenAI | 中位 78.8 ms |

多出的 60 到 85 ms 全部在 HTTP 层，热点集中在 Pydantic 的类型校验。

## 三、与 CPU llama-cpp 的对比

条件：模型也换了（jina-v5 GGUF + llama.cpp 对比 harrier + OpenVINO GPU），因此是端到端体感数据，不能把提速全部归因于设备。

| 指标 | CPU 时代 | OpenVINO GPU | 变化 |
| --- | --- | --- | --- |
| 检索平均延迟 | 58 ms | 41 ms | 快 29% |
| 短文本嵌入 | 439 到 500 ms | 34.5 ms | 约 13 倍 |
| 4096 token 嵌入 | 约 32.2 s | 3.99 s | 约 8 倍 |
| 模型加载 | 0.4 s | 3.0 s | 慢 7.5 倍 |

## 四、怎么读这组数据

**长文本提速 7.6 倍、短文本只有 1.6 倍**，不是测量误差：

1. 注意力计算是 O(n²)。6600 字（4096 token）的计算量是 30 字的几万倍，GPU 的并行核心这时才喂得饱。
2. GPU 有固定开销（调度、传输、同步）。短任务里这部分占比高，收益被吃掉大半。

所以：

| 场景 | 频率 | GPU 收益 |
| --- | --- | --- |
| 日常检索 | 最高频 | 几乎没有 |
| 写入记忆 | 中频 | 有，但被上游模型抽取时间盖过 |
| 重建向量库 | 一次性 | 巨大，200 条约 20 分钟降到约 3 分钟 |

## 五、编译缓存

首次加载模型需要编译 OpenVINO 内核，GPU 约 28 秒。编译结果缓存在 `ov_cache`，实测约 2.1 GB。

| 处理 | 后果 |
| --- | --- |
| 保留 | 重启后首次推理快 |
| 删除 | 下次启动重新编译约 28 秒，之后恢复正常 |

`ov_cache` 可以随版本升级或驱动更新失效，届时会自动重建，不影响正确性。
